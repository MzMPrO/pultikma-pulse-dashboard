## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

## Project rules (PulTikma AI)

- Architecture: React 19 + TanStack Start frontend (`src/`) and a FastAPI backend (`backend/`, `uvicorn app.main:app`). All scores come from the deterministic scoring in `backend/app/services/scoring.py`; the LLM only chats and explains. Details: `docs/ARCHITECTURE.md`.
- The frontend talks to the backend ONLY through `src/lib/api` (`import { analyze, chat, … } from "@/lib/api"`): `types.ts` (contract), `client.ts` (fetch + timeouts), `chats.ts` (user id + history), `mock.ts` (+ `mockScenarios.json`, offline fallback with the same format), `endpoints.ts`, `index.ts`. Keep the mock in sync with the backend contract (demo scenarios: Inha 84, Chilanzar 39, Novza 79).
- Frontend layout is feature-based: `src/routes` (thin file routes: head metadata + a page component), `src/features/landing`, `src/features/scout` (components, `lib/guidance.ts`, `map/`), `src/shared` (components, `map` marker helpers, `i18n`), `src/components/ui` (shadcn, do not move), `src/lib` (api, utils, error helpers). Import with the `@/` alias. Put new code in the feature that owns it; promote to `src/shared` only when two features use it.
- `src/routeTree.gen.ts` is generated by the TanStack router plugin: never edit it by hand and do not commit line-ending-only diffs.
- Routing uses TanStack Router file routes; app screen is `/app` (`/app/*` redirects to it).
- Maps: `/app` uses Leaflet + MapTiler tiles (`VITE_TILE_URL`, `VITE_TILE_ATTRIBUTION`), loaded lazily and client-only. Only the decorative landing map (`src/features/landing/map`) can use Google Maps when a browser key is present, over an SVG fallback.
- UI strings on the landing go through `useT()` from `src/shared/i18n` (ru primary, uz falls back to ru); the persisted locale store is rehydrated in `__root` to avoid SSR hydration mismatches.
- Backend layout: `app/api` (routers; `main.py` only wires the app), `app/core` (config, models), `app/services` (scoring, agent, llm, fx, chat_store, texts, geo), `app/repo` (PostGIS or CSV in memory), `backend/data` (CSV dataset + schema), `backend/scripts` (`load_data.py`, `live_data.py`), `backend/tests` (pytest). Never commit `.env` secrets.
- Checks before every commit: `npx tsc --noEmit`, `npm run build`, `npx vitest run`, and `cd backend && .venv/Scripts/python -m pytest -q -p no:warnings`. The `main` branch is synced to Lovable and must stay working.
